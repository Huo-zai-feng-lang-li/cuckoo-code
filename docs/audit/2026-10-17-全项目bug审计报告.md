## 一、执行摘要（先看这里）

本次审计共确认 **59 条 bug：P0 致命 4 条、P1 高危 15 条、P2 中危 17 条、P3 低危 23 条；另有 17 条置信度≤6 的推测项单列**。所有 P0/P1 均有 文件:行号 代码证据，关键安全项附本机实测 PoC。

### 最需要立即处置的结论

**1）X-001（P0，跨模块，本报告新增）：不可信内容可经"工具自动执行通道"在主进程静默任意代码执行，且无主进程级确认/来源校验。**
远程 AI 网页的任意脚本（页面 XSS、第三方脚本、被投毒的提供方页面），或仅靠"让 AI 读到一段恶意内容"的间接提示词注入（indirect prompt injection），就能让模型/页面调用 `window.electronAPI.executeTool('bash', …)` / `executeJs(…)`，主进程 IPC **不弹窗、不校验调用来源**直接执行；命令执行前唯一的自动闸门是 `isDangerous()` 黑名单，而该黑名单可被绕过（见 A-004）且不覆盖下载投递类命令。对照：另一条 `execute-command` 通道**每条命令都弹确认框**——说明项目具备确认能力，但自动化的工具通道恰恰没有。这是一个"远程内容 → 本机命令执行"的完整链路。

**2）A-001 / A-002（P0）：SSRF 防护两处可被直接绕过。** 用户即便开启了"拒绝访问内网地址"，webFetch 仍会跟随 302 重定向打到内网/云元数据（PoC 实测拿到内网 secret）；`http://[::ffff:7f00:1]/`（=127.0.0.1）这种 IPv4-mapped IPv6 十六进制写法守卫直接放行。

**3）E-001（P0）：恶意仓库文件 → 打开 MCP 面板即 main world XSS → 经 executeJs 直达主进程。** 项目 `.agents/mcp.json` 的 server 名未转义拼进 innerHTML，而 `.agents/` 目录 AI 本身可写、克隆恶意仓库即植入；XSS 与 X-001 合流为 RCE。

**4）D-001 / D-002 / D-004（均 P1）："打开一个项目 / 装一个插件"缺少工作区信任与第三方代码信任门。** 插件点"安装"即主进程 RCE（PoC 已实证 `whoami`）、无签名/无警告/安装即启用；项目级 MCP server 默认启用，打开恶意项目即自动 spawn 命令；项目级规则/技能全文直接拼进系统提示词。

### 修复优先级一句话
- 先堵"内容→执行"的信任边界（X-001：主进程对高危工具族强制确认 + 调用来源校验 + 黑名单仅作纵深防御）；
- 再补 SSRF 与 XSS 两类"读取/渲染"边界（A-001/A-002/E-001）；
- 再建立"工作区/插件信任门"（D-001/D-002/D-004）；
- 最后系统性修复非原子写、竞态与资源泄漏（X-004 等）。

> 说明：本应用的产品定位就是"自动执行 AI 指令"，AI 源命令本身是被信任的——这是设计前提。X-001 针对的不是"AI 能执行命令"，而是**信任边界划在了渲染层、且唯一的自动化闸门可被绕过**这两点：（a）任何能在 AI 网页执行 JS 的第三方都能直接调用主进程 IPC；（b）非黑名单命令（含下载投递、间接执行）零确认。是否需要"自动/手动"的产品取舍由用户决定，本报告只把风险与最小加固方向讲清楚。

## 三、P0 致命问题详解

### X-001｜P0｜安全（跨 A/B/C/E 链路）：不可信内容 → 主进程静默任意代码执行

**完整触发链路（输入→经过→错误输出）：**

```
输入源（任一）：
  ① AI 读到恶意网页/仓库/文件 → 间接提示词注入 → 模型回显工具调用
  ② AI 网页内第三方脚本 / 页面 XSS / 被投毒提供方
  ③ 项目文件导致的 main world XSS（E-001/E-002/E-003）
  ④ 非 DeepSeek 域名响应被当成 AI 回复（B-003）
        │
        ▼
AI 网页渲染进程（加载远程 https 页面，preload 挂 bridge/entry.js）
  window.electronAPI.executeTool(toolName, params)   src/bridge/api.ts:32-34
  window.electronAPI.executeJs(code)                 src/bridge/api.ts:44-56
  contextBridge.exposeInMainWorld('electronAPI',…)   src/bridge/api.ts:255  ← 真正向页面主世界暴露
  (window as any).electronAPI = electronAPI（兜底）    src/bridge/api.ts:261  ← contextIsolation 下仅在隔离世界赋值，不泄漏主世界（复核确认，属无害冗余）
        │  ipcRenderer.invoke('execute-tool' / 'execute-js')
        ▼
主进程 IPC（无确认弹窗、无 event.sender/来源校验）
  src/app/ipc/tool.ts:24-36  execute-tool → toolRegistry.execute(...)
  src/app/ipc/tool.ts:39-69  execute-js → jsRunner.run(...)
  src/tools/core/ToolRegistry.ts:45-55 execute() 内部同样无审批闸
        │
        ▼
工具执行（自动执行，无确认）
  bash.ts:128-130  唯一闸门 isDangerous(trimmed)，命中即拒、否则 exec
  pwsh.ts 同理；黑名单 src/infra/dangerous-commands.ts（可绕过，见 A-004）
        │
        ▼
结果：非黑名单命令（含 powershell -enc、curl|iex、certutil、node/python 脚本、
      cmd /c 等）在用户毫不知情的情况下静默执行 → 任意代码执行/数据窃取/持久化
```

**关键对照证据：**
- 平行的 `execute-command` 通道（`src/app/ipc/command.ts:27-38`）对每条命令都 `dialog.showMessageBox`，且 `result.response !== 1` 即取消。**自动化主通道 `execute-tool` 没有任何等价物。**
- AI 视图 webPreferences（`src/app/entry.ts:177-180`）：`contextIsolation:true / nodeIntegration:false / sandbox:false`，preload 为 `bridge/entry.js`。隔离本身配置正确，但 contextBridge 把含 executeTool/executeJs 的整套 API 暴露给了该远程页面的主世界——页面自身的脚本与注入的 onerror 处理器都能访问。
- 黑名单文件头注释自承局限（`dangerous-commands.ts:12-13`）："无法可靠拦截 `cmd /c \"…\"`、变量展开、脚本文件等间接方式。生产环境应叠加白名单或强制用户确认。"

**为什么定级 P0：**
- 入口只需"让 AI 读到一段内容"（间接提示词注入是当前 agentic 应用最现实的攻击面），无需页面 0day；
- 全程无确认、无来源校验；
- 黑名单非安全边界（A-004 已实证 6 类绕过，且不覆盖下载投递/反弹 shell）。

**置信度：** 8/10（链路每个环节均已 Read 原文核对，A-004 绕过有 PoC；"模型必然被间接注入"属概率事件，故不给满分，但即便无注入，入口②③也已成立）。

**修复建议（最小、纵深）：**
1. **主进程强制审批**：在 `execute-tool` / `execute-js` 主进程入口对高危工具族（bash/pwsh/write/edit/deleteFile/webFetch/attachFile/injectJS 等）增加确认/策略开关，确认逻辑必须在主进程（渲染层任何开关都可被绕过），与 `execute-command` 对齐；
2. **调用来源校验**：IPC handler 校验 `event.sender` 归属的窗口/视图与 `event.senderFrame.url` 的 host 是否在允许的 provider 白名单内；
3. **收敛/监护 preload 暴露面（次要）**：真正向主世界暴露的是 `api.ts:255` 的 `contextBridge.exposeInMainWorld`（这是 harness 工作所需，不能简单移除），因此重点不是删暴露面，而是为暴露的 executeTool/executeJs 建立"可信来源+受控调用"约束（见第 1、2 条，主进程侧确认与 sender/host 校验才是真正的闸）。注意 `api.ts:261` 的 `(window as any).electronAPI = electronAPI` 兜底，经复核在 `contextIsolation:true`（entry.ts:178）下只在 preload 隔离世界赋值、**不泄漏到主世界**，属无害冗余，移除它仅是整洁性清理而非安全修复；
4. 黑名单（A-004）补齐、SSRF（A-001/A-002）、XSS（E-001/E-002/E-003）作为纵深防御同步修，但**不能替代** 1/2。

> 本条由 Organizer 在汇总 5 片后新增：它合并并升级了 C-006（原 P2/推测）与 C 片 S-001（原推测区"sender 系统性不校验"），这两处不再单列。

### A-001｜P0｜安全（SSRF）：webFetch 跟随 302 重定向，内网/云元数据可被读取
- 位置：`src/tools/impl/web-fetch.ts:141-146`（fetch 前仅校验首跳 URL）、`:159-162`（`fetch(url, { method:'GET', signal })`，未设 `redirect:'manual'`，undici 默认 follow）。
- 链路：开启 SSRF 防护 → AI 抓取公网 URL → 该 URL 返回 `302 Location: http://169.254.169.254/…` 或 `http://127.0.0.1:port/…` → 首跳公网放行 → 自动跟随 → 内网/云元数据内容被取回并回传 AI。
- PoC：`.agents/audit-poc/poc-2-ssrf.mjs` 实测跳板 302 后拿到内网 secret body。
- 置信度 9；测试盲区：`test/tools/WebFetchTool.test.js` 全部只测纯函数，无 fetch/重定向用例。
- 修复：`redirect:'manual'` 后对每跳 Location 再 `assertUrlAllowed`（限跳数），或 follow 后对 `response.url` 复检。

### A-002｜P0｜安全（SSRF）：IPv4-mapped IPv6 十六进制写法直穿守卫
- 位置：`src/infra/ssrf-guard.ts:66` `s.match(/^::ffff:(\d+\.\d+\.\d+\.\d+)$/)` 只认点分式。
- 链路：`http://[::ffff:7f00:1]/`（=127.0.0.1）、`http://[::ffff:a9fe:a9fe]/`（=169.254.169.254）→ 判为 IPv6 且 mapped 不匹配 → 放行 → 直连回环/链路本地。
- PoC：`poc-2-ssrf.mjs` 实测 `isBlockedIp('::ffff:7f00:1')===false`、`assertUrlAllowed` 放行；对照组 `0x7f000001`/十进制/前导零已被 WHATWG 归一化正确拦截（排除误报）。
- 置信度 8；测试盲区：`test/infra/ssrf-guard.test.js` 无十六进制 mapped 用例。
- 修复：用标准库把 IPv6 归一（解析为 32 位整数取低 32 位当 IPv4 判定）。

### E-001｜P0｜安全（DOM XSS→IPC）：项目 .agents/mcp.json 的 server 名未转义注入
- 位置：`src/overlay/panels/mcp-manager.ts:46-47`，`s.name` 原样拼进 data 属性与文本；`src/mcp/config.ts:155-175` 全链路无转义。
- 链路：恶意仓库/被诱导的 AI 写入 `.agents/mcp.json`（server 名形如 `x"><img src=x onerror=…>`）→ 项目级 server 默认启用 → 用户打开悬浮窗 MCP 面板 → 注入 HTML 在 AI 网页主世界执行 → 调 `window.electronAPI.executeJs/executeTool`（接入 X-001）。
- PoC：`.agents/audit-poc/poc-overlay-mcp-name-xss.cjs` 实测 `<img onerror>` 原样输出。
- 置信度 9；测试盲区：`test/overlay/panels/mcp-manager.test.js` 只测保存校验。
- 修复：内容位 `escapeHtml`、属性位 `escapeAttr`，与 shell 侧 `pages/mcp.ts:24-33` 对齐。

## 四、P1 高危问题一览（要点，完整证据见分片报告）

**安全类**
- **A-003 受保护路径大小写绕过**（`src/infra/protected-paths.ts:31-34`）：Windows 大小写不敏感但守卫用 `===`/`startsWith`，`Snapshots/evil.txt`、`Memories.json` 变体可写入/覆盖快照存档与用户记忆。PoC 实测覆盖 memories.json 为 "pwned"。置信度 9。

- **D-001 插件安装即主进程 RCE**（`src/plugins/cuckoo-plugins/loader.ts:280-281` 传入主进程完整 require；`installer.ts:191` npm install + `index.ts:130` 安装即启用）：点"安装"=RCE；无包名白名单、无 hash/签名、无二次警告；curated 还含第三方反代 ghproxy（D-007）。PoC 实测 `whoami` 返回 `zk\administrator`。置信度 10。
- **D-002 项目级 MCP server 默认启用**（`src/mcp/config.ts:190` `enabled: state[name] !== false`）：打开恶意项目即自动 spawn `.agents/mcp.json` 里的命令，无确认。置信度 9。
- **D-003 MCP HTTP server URL 无校验（SSRF）**（`src/mcp/client.ts:189-192`）：项目配置可指向云元数据/内网。置信度 8。
- **D-004 项目级规则/技能全文注入系统提示词**（`src/rules/prompt.ts:20`、`src/skills/prompt.ts:17`）：克隆恶意仓库即提示词注入，无"工作区信任"门。置信度 9。

**可靠性/数据类**
