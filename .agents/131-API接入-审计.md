## 3. 缺陷与风险取证清单

### [🔴 严重] 停止/抢占后留下孤儿 `assistant(tool_calls)`，下一轮必 400
- **定位**：`src/api-transport/runtime.ts:210-231`（尤其 `:218`）
- **事实证据**：
  - `:210-215` 先把带 `tool_calls` 的 assistant 消息 `push` 进历史，`:217-230` 再逐个执行并 push `role:'tool'`。
  - `:218` 在 for 循环开头 `if (controller.signal.aborted) return`；`stopApiSession` / 新一轮抢占（`:139-142`）都会 abort。
  - `trimHistory`（`:65-72`）只按 `user` 边界切，无法消除这种半截结构。
  - 推演路径：模型返回 tool_calls → 用户点停止（或连发第二条）→ abort → 在工具执行中/循环首行 return → 历史里留下 `assistant(tool_calls)` 且无对应 `tool` 消息 → 用户再发一条 → 携带该畸形历史请求 → OpenAI 兼容端点返回 400（`tool_calls must be followed by tool messages`）。
- **潜在危害**：停止后这一窗口的 API 对话彻底不可继续（只有「新对话」能救），且错误信息是网关 400，用户无法理解。
- **修复方案**：在执行工具前记录 `lenBeforeToolCalls`；abort 时回滚（`st.messages.length = lenBefore`），或对每个未回传的 call 补一条 `{role:'tool', tool_call_id, content:'(cancelled)'}`。
- **信心评分**：9 / 10

### [🟡 中等] 异常终态被当成"消息发送失败"，并回填草稿导致重复发送
- **定位**：`src/api-transport/runtime.ts:197-204 / 234-239 / 241`；`src/ui/harness.html:5282-5288 / 5511-5521`
- **事实证据**：工具开关关闭、工具轮数超限、用户停止三条路径都返回 `{success:false}`；前端 `send()` 仅按 `res.success === false` 判失败 → `appendSystem('消息发送失败：…')` + `settleDraft(false)` → 输入框为空时把原文回填。
- **潜在危害**：消息其实已经入历史、界面也已有输出，却提示失败并把原文塞回输入框，用户重发 → 重复提问、重复执行工具（可能重复写文件）。
- **修复方案**：返回结构增加 `code: 'stopped'|'rounds-exceeded'|'send-failed'`，前端只在"未入队"时回填草稿与报失败。
- **信心评分**：9 / 10

### [🟡 中等] 流式请求无总超时，IPC 单次 invoke 挂整轮
- **定位**：`src/api-transport/client.ts:227-238`；`src/app/ipc/harness.ts:250`
- **事实证据**：`while (!done) { await reader.read() }` 只依赖 `[DONE]` / 流结束 / 手动 abort，没有总时限；`sendApiMessage` 被 `harness-send` 直接 `await`，一轮含工具可能持续数分钟。
- **潜在危害**：网关卡住或永不发 `[DONE]` 时本轮永不收敛（除用户手动停止）；需求文档里承诺的"总超时"未落地。
- **修复方案**：`streamChat` 增加 `overallTimeoutMs`（与用户 signal 用 `AbortSignal.any` 合并），超时 abort 并返回明确错误。
- **信心评分**：8 / 10

### [🟡 中等] API 模式无法设定项目目录，且「用项目新建对话」静默丢弃所选目录
- **定位**：`src/app/ipc/harness.ts:1033-1038`；`src/ui/harness.html:6407-6410`；`src/app/ipc/session.ts:496-503`
- **事实证据**：API 分支 `needInit: false` → 唯一入口 `#init-project-btn`（`harness.html:1172`）恒隐藏；`startNewConversationForProject` 的 API 分支只 `resetApiSession + prepareNewConversation`，未写 `sessionStore.state.selectedProjectDir`。`tool-loop.ts:125` 的 `projectDir` 取自该状态。
- **潜在危害**：`projectDir=null` → `isWorkspaceTrusted(null)` 恒 false → 敏感工具每次弹确认或直接拒绝；用户明确选的目录被丢掉（典型伪闭环）。
- **修复方案**：API 模式把 `needInit` 改为 `!hasProjectDir`（但仍不注入 initial-prompt）；`startNewConversationForProject` API 分支显式写入 `selectedProjectDir` 并走 `ensureWorkspaceTrust`。
- **信心评分**：8 / 10

### [🟡 中等] 窗口关闭不中止请求，`sessions` Map 永不淘汰
- **定位**：`src/api-transport/runtime.ts:24 / 105-127`；`src/app/entry.ts:893-898`
- **事实证据**：`sessions` 只有 `getState` 写入，无删除入口；`mainWindow.on('closed')` 只 `removeWindow / forgetWindow`，不 abort controller、不 `abortWindowProcesses`。
- **潜在危害**：关窗后 fetch 与工具子进程继续跑并写盘（孤儿进程 + 内存常驻）；删除 profile 后同样残留。
- **修复方案**：导出 `disposeApiSession(windowId)`，在 `closed` 与 `delete-profile` 中 abort + `abortWindowProcesses` + `sessions.delete(key)`。
- **信心评分**：9 / 10

### [🟡 中等] 启动对账缺少空列表守卫，异常时会清空全部窗口组
- **定位**：`src/app/entry.ts:1985-1990`；`src/app/window-groups.ts:208-214`；`window-groups-reconcile.ts:22-60`
- **事实证据**：`validIds = readProfiles().map(...)`；`reconcileWindowGroups` 只按 `valid` 集合过滤，`validIds=[]` 时所有组被判 `kept.length===0` → 丢弃并写盘。`readJsonRobustSync` 损坏时回退 `DEFAULT_DATA` 不会救这里（那是 groups 文件，不是 profiles 文件）。
- **潜在危害**：profile 列表因损坏/首启读空时，用户全部窗口组与限流记录被写成空（有 `.bak` 可手工恢复，但无提示）。
- **修复方案**：`pruneMissingProfiles` 在 `validIds.length === 0` 时直接 `return false`。
- **信心评分**：7 / 10（取决于 readProfiles 何时会返回空）

### [🟡 中等] 重试时已流出文本被新一轮覆盖；`sleep` 的 abort 监听器泄漏
- **定位**：`src/api-transport/client.ts:127-139`；`:66-76`
- **事实证据**：429/5xx 重试从头 `once()`，UI 侧 `onStream` 以"全量快照"渲染（`harness.html:3977` 注释明确），新尝试的短文本会把已显示的长文本覆盖回短。
- **潜在危害**：用户看到文字先出现再"缩回去"重来；`setTimeout` resolve 后未 `removeEventListener`，每次重试残留一个 abort 监听器（上限 2 次，影响很小）。
- **修复方案**：重试前发一次 `onText('', '')` 复位；`sleep` 在 resolve 分支移除监听器。
- **信心评分**：8 / 10（文本回退）/ 9 / 10（监听器）

### [🟡 中等] `todoWrite` 在 API 模式不推计划面板
- **定位**：`src/api-transport/tool-loop.ts:129-134`（对比 `src/app/ipc/tool.ts:67-87`）
- **事实证据**：plan 推送只存在于 `execute-js` 分支（读 `globalThis.__cuckooTodos[projectDir]`）；`tool-loop` 直接 `registry.execute` 后未推送；`runtime.ts` 仅在发送前清空一次 `todos: []`。
- **潜在危害**：模型调用 `todoWrite` 后 harness 计划面板永远空，用户看不到进度（功能半截）。
- **修复方案**：`tool-loop` 执行后复用 tool.ts 的去重推送逻辑（`lastTodosJson` + `emit plan`）。
- **信心评分**：8 / 10

### [🟡 中等] API Key 明文落盘，与注释承诺不符
- **定位**：`src/api-transport/config.ts:6`；`src/app/ui-prefs.ts:232`；`src/ui/harness.html:6064`
- **事实证据**：注释写「Key 只在主进程内存中使用」，但 `writePrefs` 把 `apiTransport.apiKey` 原样写入 `ui-prefs.json`。
- **潜在危害**：本地明文长期保存，备份/同步/其它进程可读取。危害级别取决于用户环境（局域网无鉴权网关场景风险低）。
- **修复方案**：改注释措辞，或用 `safeStorage.encryptString` 后存储。
- **信心评分**：9 / 10（明文事实）/ 风险自知
