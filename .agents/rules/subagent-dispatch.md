# 派发子代理的硬约束

> 子代理是**完全无状态**的独立会话，没有任何上下文记忆。
> 所有派发必须遵守本协议，否则会出现"子代理反复读文件试图对齐上一轮，卡到超时"。

## 硬约束

1. **严禁伪连续措辞**
   - ❌ "上一轮你提的问题已按以下方式处理……"
   - ❌ "如前所述"、"你之前指出"、"接着上次"
   - 子代理没有"上一轮"和"上次"，它只有你这次给它的一段文字。

2. **自包含上下文（三要素必须齐全）**
   - **【用户原始目标与痛点】**：要解决什么实际问题 / 防御什么场景。
   - **【主代理修复逻辑】**：采用了什么方案，处理了哪些根因，改了哪些文件。
   - **【待检源码文件】**：绝对路径 + 相关调用链，让子代理不用猜去哪找。

3. **闭环原则**
   - 主代理必须逐条复核子代理意见，**不得盲目听信**。
   - 确认是真问题 → 修复 → 再次验证。
   - 无法确认的，标注"待验证"，不静默丢弃。

4. **失败诊断**
   - 子代理卡住 / 超时 / 结果偏离，**先怀疑 prompt 信息不足**，而不是先怀疑子代理能力。
   - 复盘子代理时，重发完整自包含任务，不要试图"接着上一轮"。

## 反例（真实事故）

主代理对全新子代理写：
> "上一轮你提的问题已按以下方式处理，请验证修复是否正确：1. set() 改为……"

子代理反应：反复搜索文件试图找到"上一轮"的依据 → 找不到 → 一直找 → 495 秒未返回。

正确写法：
> "## 用户原始目标
Android 应用图标切换（activity-alias）。

## 修复逻辑
之前的问题是切换时先 disable 旧 alias 再 enable 新，若 enable 抛异常会导致零 launcher。现改为先 enable 目标、落盘、再 disable 其余。

## 待检文件
- D:/xxx/AppIconPlugin.java（重点 L105-151）

## 请核验
1. 新顺序是否真的消除零 launcher
2. ……"

## 并发派发规范（Parallel Dispatch）

子代理 MCP 现已原生支持**全并发非阻塞派发**与**多 Key 负载均衡**：
1. **模型与推理强度**：子代理固定采用 **max 顶级深度推理**，优先使用 **3.0 (agnes-3.0-flash)**；若发生超时或网关异常，系统将自动无缝平滑降级为 **2.5 (agnes-2.5-flash)** 并维持 max 推理完成审查。
2. **多维度并发审查**：复杂场景或重构任务推荐使用 `invoke_subagents_parallel`（或 `invoke_subagent` 传入 `tasks` 数组）并发派出多个聚焦不同维度的子代理：
   - 角色 1：【并发与竞态安全审计】（聚焦死锁、时序竞争、单例竞态、异步顺序）
   - 角色 2：【架构与代码质量审查】（聚焦圈复杂度 ≤ 9、职责单一、设计模式与扩展性）
   - 角色 3：【边界与异常防御审计】（聚焦空指针、解构未定义、文件与监听器泄露、非法入参）
3. **并发自动汇总**：多个子代理在云端完全并行执行，各自独立产出报告，并自动汇集成统一的综合审查面板置顶交付。
