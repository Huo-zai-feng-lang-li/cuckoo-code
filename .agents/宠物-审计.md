# 宠物（纯净模式 + 桌面浮窗）- 对抗性代码审计报告

## 1. 门禁裁决
- **裁决结果**：🛑 REJECT（发现 1 处 🔴 打包断链）
- **审计范围**：暂存区（`git status -s` 左侧位全部为暂存）；实际审计 46 项变更，其中代码/配置 20 个文件（+约 1350 行），图片 20 张、生成物 1 个；已剔除 2 个临时脚本 `tmp-bubble-check.mjs` / `tmp-css-check.mjs`（不应入库，且会随 asar 打包）
- **裁决理由**：`package.json` 的 `build.files` 白名单未加 `src/ui/pets/**`（也未同步 `out/src/ui/pets/**`），打包后 harness 页与桌面宠物页的三处引用会 404；叠加临时脚本入库、脏工作区构建静默失败，当前状态不可发布。

## 2. 改动链路与闭环核验
- **核心改动摘要**：新增精灵图宠物（`pet.js` 渲染器 + `pack.json` 真源 → `build-pets.mjs` 生成 `pets.generated.js` → `copy-pets.mjs` 拷到 out）。纯净模式把右上角状态条 `.sr-only` 视觉隐藏（DOM 保留作运行态载体），文案全部迁到宠物双层气泡（下层状态含秒数、上层情绪）；新增独立桌面浮窗 `pet-window.html`，主窗口 minimize 显示 / restore 隐藏，状态经 `harness-pet-state` 由 harness 单向推给主进程。
- **两端闭环取证**：
  - 起点（触发/输入）：`src/ui/harness.html:4104` initPet（读 `getUiPrefs` → `CuckooPet.create`）；`src/app/entry.ts:218` `mainWindow.on('minimize')` → `syncPetWindow()`（已核实）
  - 终点（呈现/落盘）：`src/ui/pets/pet.js:256` `paint()` 逐帧切图（已核实）；`src/app/ui-prefs.ts:199` `writeJsonAtomicSync` 落盘 petSize/petDesktopSize/petX（已核实）
  - 桌面窗口状态收敛：`src/app/pet-window.ts:65 pushState` → `pet-window-preload.ts:16 onState` → `pet-window.html:140 applyState`（已核实）
  - Untracked 漏提风险：无（`git status` 无 `??`；但**反向问题**：临时脚本被 add 了，见 #3）
  - **打包闭环：断链**（见 #1）

## 3. 缺陷与风险取证清单

### [🔴 严重] 打包 files 白名单缺 pets 目录 → 安装包内宠物资源整体缺失
- **定位**：`package.json:141-188`（`build.files`）
- **事实证据**：
  - `grep -n "src/ui/(notif-images|vendor)" package.json` 显示白名单为显式逐条：`"src/ui/*.html"`、`"src/ui/notif-images/**"`、`"src/ui/feishu-images/**"`、`"src/ui/vendor/**"` —— **没有 `src/ui/pets/**`**。
  - 引用点：`src/ui/harness.html:12,1184,1185`、`src/ui/pet-window.html:7,51,52` 均为 `pets/pet.css` / `pets/pets.generated.js` / `pets/pet.js`。
  - 生成物落到 `out/src/ui/pets/`（`scripts/copy-pets.mjs:12`），`out/**` 未被任何白名单条目覆盖。
  - `src/ui/` 下只有 `shell/`（真源）与 `pets/`（新）两个子目录，二者都不在 files 列表里。
- **潜在危害**：开发版（`APP_ROOT`=项目根）一切正常，**打包版** `harness.html` 无宠物且状态条已被 `sr-only` 隐藏 → 状态文案**彻底不可见**（比不装宠物更糟）；桌面浮窗白屏、`did-finish-load` 后宠物对象为 null，用户只会看到"最小化后什么都没有"。真机验证走的是开发版，覆盖不到此路径。
- **修复方案**：`files` 增加 `"src/ui/pets/**"`（与 `src/ui/*.html` 同级，覆盖 out 镜像）。若要保险可显式补 `"out/src/ui/pets/**"`。
- **信心评分**：9 / 10（唯一不确定项：electron-builder 是否把 files 条目从 APP_ROOT 而非 out 解析——但即使用 out 解析，条目也必须存在才匹配，结论不变）

### [🟡 中等] 临时调试脚本被暂存，会入库并打进安装包
- **定位**：`tmp-bubble-check.mjs`、`tmp-css-check.mjs`（暂存区 A 状态）
- **事实证据**：两个文件硬编码 CDP 端口 `127.0.0.1:9444`、按窗口标题 `Cuckoo Harness` 抓 target，属于一次性真机调试脚本；`build.files` 的排除列表里没有 `tmp-*`/根目录 `*.mjs`，会被 asar 打进去。
- **潜在危害**：仓库噪音 + 安装包里多两个依赖本地 CDP 的死脚本；后人误以为它们是正式工具。
- **修复方案**：`git rm --cached tmp-bubble-check.mjs tmp-css-check.mjs`（保留工作区）或直接删除。
- **信心评分**：10 / 10

### [🟡 中等] 生成物与真源不同步：`pets.generated.js` 是"未暂存的 A 文件"，首次构建还会导致 shells 静默漂移
- **定位**：`src/ui/pets/pets.generated.js`（status 曾为 `A`，重跑 build 后变 `MM` 又转回 `A`，见下）
- **事实证据**：`node scripts/build-shell.mjs && node scripts/build-pets.mjs && node scripts/build-docs-index.mjs` 后 `git status` 出现 `MM src/ui/shell.html`，紧接着 `git diff src/ui/shell.html` 为空 —— 说明这份生成物存在**索引与工作区不一致**的历史状态（本会话内已被一次重建"洗白"）。另外 `pet.js` 里 `SIZE_PX`、`MAX_PX` 等常量与 `src/app/ui-prefs.ts` 的 `PET_SIZE_MIN/MAX` 是两份独立真源（48/256 各写一遍）。
- **潜在危害**：提交的生成物与真源不一致 → CI/别人重跑 compile 产生 diff；两处尺寸常量将来只改一处会静默分叉。
- **修复方案**：提交前统一跑一次 `npm run compile` 再 `git add` 全部生成物；`pet.js` 的尺寸上下限加注释指向 `ui-prefs.ts`（或由 build-pets 注入）。
- **信心评分**：8 / 10

### [🟡 中等] `.sr-only` 与 `statusEl.className` 双写，两处字符串拼接易漏
- **定位**：`src/ui/harness.html:1841`、`src/ui/harness.html:3271`（`setStatus`）
- **事实证据**：`grep -n "statusEl.className"` 只有这两处：会话重置路径写 `'status ready sr-only'`，`setStatus` 写 `'status sr-only' + state`。已有代码里 `statusEl.classList.contains('busy')`（:3100）和 `.sending`（:3121）依赖 class 集合；把 `sr-only` 塞进同一字符串后，任何将来新增的 `statusEl.className = ...` 只要漏掉 `sr-only`，状态条就会**视觉复活**（与宠物气泡重复）。
- **潜在危害**：回归悄无声息（没有测试覆盖 DOM class 组合）；用户会看到"顶部一行状态条 + 宠物气泡"两份文案。
- **修复方案**：把视觉隐藏做成独立声明，例如 CSS `.status { ... }` + `#status { position:absolute; ... }` 或统一走 `statusEl.classList.toggle('sr-only', true)`，避免字符串拼接。
- **信心评分**：8 / 10

### [🟡 中等] 桌面浮窗"驱动窗口"状态机在窗口销毁后不清理
- **定位**：`src/app/ipc/harness.ts:49,683-684,705-713`
- **事实证据**：`petDriverWinId` 只在 `harness-pet-state` / `harness-set-busy` 里赋值/置 null，窗口关闭路径（`entry.ts:222 mainWindow.on('closed')`）只 `destroyPetWindow()`，不重置 `petDriverWinId`。推演：窗口 A 忙 → `petDriverWinId=A` → A 被关闭 → 新窗口 B 空闲推 `{state:'idle'}`，走 :681 `!incomingBusy && !isActive`（B 尚未成为 lastActive）直接 return；B 成为 active 后推 idle，走 :684 `petDriverWinId !== null && !== B` → return。结果：**宠物停在 A 最后的忙态/文案上**，直到 B 开始忙。
- **潜在危害**：桌面浮窗显示"工具执行中 7s"等永不结束的僵尸文案（秒数不涨、也无法被空闲状态复位），用户以为任务还在跑。
- **修复方案**：在 `windowState.removeWindow` 的调用方（`entry.ts` 的 `closed` 处理）里加一句重置：把 `petDriverWinId` 的清理导出成 `resetPetDriver()`，或在 `harness-pet-state` 里判断 `petDriverWinId` 对应的 ctx 是否还存在（`getWindowContext(petDriverWinId)` 为 null 则视为未锁定）。
- **信心评分**：7 / 10（依赖"关窗后不再有新窗口推 idle"这一时序，未真机复现）

### [🟡 中等] `pet-window.ts` 窗口尺寸只在 `showPetWindow` 时按偏好算，`minimize` 复用时忽略尺寸变化
- **定位**：`src/app/pet-window.ts:73-78`（幂等分支）
- **事实证据**：`if (petWin && !petWin.isDestroyed()) { showInactive(); pushState(); return; }` —— 直接返回，不比较 `size`。而 `entry.ts:214 syncPetWindow` 每次都从 `readPrefs()` 取最新 `petDesktopSize` 传进来。若用户在设置里改了桌面宠物大小（`applyPetPrefs` → `setPetWindowSize`，但那一步有 `isPetWindowVisible()` 守卫，窗口隐藏时**不会执行**），再最小化主窗口，宠物会以**旧尺寸**出现，直到窗口被销毁重建。
- **潜在危害**：设置项看起来"不生效"（实际只在首次生效），属于用户可感知的功能缺陷。
- **修复方案**：幂等分支里补 `setPetWindowSize(size)`（该函数已按 `boundsFor` 计算并保持右下角锚点，幂等安全）。
- **信心评分**：8 / 10

### [🟢 轻微] `pet.js` 6 处未使用形参 `e` 触发 lint 警告
- **定位**：`src/ui/pets/pet.js:446,459,476,482,483,516`
- **事实证据**：`npx eslint src/ui/pets/pet.js` → 6 个 `no-unused-vars` warning（0 error；`.ts` 文件被 eslint 配置忽略，全量 lint 仍是 0 errors / 71 warnings）。
- **潜在危害**：无功能影响；与仓库"0 problems"纪律有出入（虽为 warning）。
- **修复方案**：把 `catch (e) { /* ignore */ }` 改为 `catch { /* ignore */ }`（该文件已用 `try { ... } catch { /* ignore */ }` 的写法，见 :445）。
- **信心评分**：10 / 10

## 4. 五维核查矩阵回执
- [x] **架构契约与安全红线**：见 #1（打包白名单）。依赖方向合规：`pet-window.ts` 只依赖 `infra/paths` + `app/window`；`ipc/harness.ts`/`settings.ts` 未新增反向依赖；主进程用 `createRequire('electron')` 符合铁律；preload 走 `contextBridge`、`sandbox:false` 与 alert/notification 窗口一致。安全：无硬编码密钥；`html: true` 只渲染程序拼的 `<b>Ns</b>`，无用户输入进入 `innerHTML`（`petBubble` 调用点全部是字面量或 `petSec()`）；CSP 未放宽（`pet-window.html:5` 保留了 `script-src 'self' 'unsafe-inline'`，与 harness 一致）。
- [x] **端到端功能闭环**：开发态闭环成立（见第 2 节两端取证）；**打包态断链**见 #1；桌面浮窗状态推进见 #5。
- [x] **对抗性 Bug 与并发安全**：见 #5（驱动窗口僵尸态）、#6（尺寸不刷新）。已核查并排除：`pet.destroy()` 会 `cancelAnimationFrame` + `clearTimeout(hintTimer)` 并摘 DOM（`pet.js:566-571`），重建路径 `boot()` 先 destroy 再 create，无 RAF/定时器泄漏；`document.hidden` 冻结（`pet.js:334`）避免后台耗电；`setTimeout(maybeFlushQueue)` 等既有逻辑未被破坏；`petBubble` 里 `api.setPetState` 失败被 try/catch 吞掉，不影响对话主流程（符合"宠物纯装饰"设计目标）。
- [x] **性能与代码复杂度**：`pet.js` 单 rAF 驱动、`snapCSS` 只在切帧/改尺寸时写 style，无每帧全量布局读；`pack.json` 逐帧压平成扁平数组，运行时无对象分配；`build-pets.mjs`/`copy-pets.mjs` 为一次性构建脚本。`ipc/harness.ts:671-714` 两个处理器分支 ≤4 层、无循环，圈复杂度在门限内。
- [x] **领域专项**：
  - **专项 A（AI Agent 运行时）**：`harness-pet-state` 为**纯出站**通道（`ipcRenderer.send`，主进程无回传），不触碰会话上下文/Messages 数组，不构成"可见历史 vs 实际上下文"风险；忙态准入仍由既有 `setBusy`/队列控制，宠物不新增输入穿透点。
  - **专项 B（前端状态机）**：`.sr-only` 双写见 #4；气泡两层语义分离（sticky→status 层、瞬时→hint 层）在 `bubble()` 里用 `hintTimer` 还原，未发现"瞬时提示结束后情绪层丢失"路径（`moodText` 保留）。
  - **专项 C（存储）**：`ui-prefs.json` 走既有 `writeJsonAtomicSync`（临时文件 + rename），新增字段全部经 `normPetSize`/`clampPetX` 钳位，旧配置（`petSize` 为 `small/medium/large` 字符串）有 `LEGACY_PET_SIZE` 兼容映射。
