## 四、性能评估

### 正向优化（已验证）

| 优化点 | 效果 |
| :--- | :--- |
| `chunks: string[]` + `join('')` 替代 `msg += …` | 避免 O(n²) 字符串拼接，长工具输出场景明显 |
| `readCachedText`（mtimeMs+size） | 省去每轮提示词构建的同步 readFileSync（3 个文件 × 每次交互） |
| `directorySignature`（目录 + 文件签名） | 规则扫描由 O(N 读全文) → O(N stat) 或 O(1) 内存命中 |
| `estimateTokens` 单次字符遍历 | 省去 5 次 `String.match(/…/g)` 的中间数组分配；surrogate pair 处理正确（`i++` + 计数扣除） |
| `isElementVisible` 优先 `checkVisibility` | 避免强制 Layout 重排 |
| `getInputText` 空输入框走 `textContent` | 高频探测（每次 sendStateChanged）场景受益，非空时仍回退 `innerText`（1 次 layout） |
| `pushTps` 150ms 节流 | 高频流式期间 IPC 下降至约 6~7 次/秒 |
| `findSendButton(knownInput)` 复用输入框 | 重试 14 次时不再每次全量扫 15 个选择器 |

### 待观察点

- **`chat-input.ts` 圈复杂度**：`findInputArea`（缓存/Provider/textarea/editable 四分支）、`fallbackSend`（Provider 按钮/表单/Enter 三分支）、`sendButtonWithFallback`（点击/表单/Enter 三回退）——每个函数分支数 3~4，**均 < 9，达标**。但 `fallbackSend` 与 `sendButtonWithFallback` 存在"发送方式"职责重叠，若继续扩展建议抽出策略表。
- **`deepseek.findSendButton` 候选扫描**：策略 1 在 5 层祖先内 `querySelectorAll('button, div[role="button"]')`，命中 `isSafeButton` 会触发 `closest` 祖先链。长页面极端情况下每层可能几十个候选。当前重试上限 14 × 每层数十次遍历可接受，**建议后续加 depth 内 "has svg" 快速初筛**。
- **`createResponseDecoder` 的 buffer**：无换行时累积，直到出现 `\n`。若上游 chunk 极大（> 数百 KB）会瞬时膨胀，属正常流式解码行为，非缺陷。

### 内存与句柄

- `activeNotifications` Set：`click`/`close` 双向清理，**有界**。
- `textCache` / `scanCache`：键为固定文件路径与固定 rulesDir，**有界**。
- `cachedInputArea`：单值，**无泄漏**。
- observer `safetyTimer`：成功路径 `dismissMask` 清理，cancelled 分支显式 `clearTimeout`，**无泄漏**。

**性能判定：无新增性能退化；本 diff 为净收益优化。**
